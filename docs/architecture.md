# Architecture and environment boundaries

## Data ownership

The app is a native client of the existing website backend. It never connects to PostgreSQL, Directus administration or internal services directly. All authorization, membership decisions, pricing, event capacity and payment verification happen on the server.

The app code and widget extension live only in this repository. Versioned HTTP endpoints and the notification worker live in a separate backend branch based on the website's `acceptance` branch. That branch must never target `main` as part of this work.

## Acceptance first

- Default API origin: `https://acc.salvemundi.nl`.
- API prefix: `/api/mobile/v1`.
- Backend requires both `ENV_NAME=acc` and `MOBILE_API_ENABLED=true`; other environments return 404.
- No automatic production promotion, database migration or notification activation.
- Acceptance and production share core database infrastructure in the website configuration. Their actual database names must be compared by an operator before migrations. Acceptance-only code is not a guarantee of isolated data.
- App-only notification tables are environment-scoped. Delivery is independently disabled by default and must be restricted to approved test users and APNs sandbox devices during acceptance testing.

## Identity and payments

Microsoft login opens in the system authentication browser. A PKCE-bound, single-use authorization handoff returns to `salvemundi://auth/callback`; the app exchanges the code over HTTPS. The app stores its revocable credential in Keychain. Logout clears personal caches and widget summaries, and asks the backend to revoke the session/device association.

Only an authorization code and state may appear in the login callback. Session credentials, Microsoft tokens and member data must never be put in callback URLs or logs.

Activity registration reuses website domain logic. Mollie checkout is opened in the browser; returning to the app refreshes server state. A successful browser return alone does not prove payment. Payment webhooks remain authoritative.

## Offline and widget privacy

Activities and previously fetched tickets can be displayed offline, with a stale-data indication. Registration, profile changes and payment verification require connectivity. Existing QR credentials are never regenerated by the client, and offline copies do not override scanner-side validity.

Widgets receive only the event summaries they need through an App Group. Snapshots contain neither authentication credentials nor QR tokens. Personal event summaries are privacy-sensitive and must be cleared on logout. Widget refreshes are opportunistic, not a real-time delivery guarantee.

## Other features

Administration, complete trip/intro management, pizza and merchandise remain website destinations. Do not reproduce their workflows in the app without extending the API contract and tests first.
